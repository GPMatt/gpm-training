Orientation

What the system does, in one pass

Employees buy things on the company credit card and submit a photo of each receipt through a Google Form. Once a month the bank sends one statement PDF listing every charge on that card. This system's whole job is to pair each submitted receipt with the real charge that matches it, then bill the property owner for it in QuickBooks — one invoice per owner, with the receipt images attached.

Alaina used to hunt through Drive folders and build 100–200 QuickBooks invoices by hand every month. Steps 1–8 below replace that.

What happens without you

Four jobs run on their own. You don't start them and you don't wait for them:

WhenWhat runsWhat it does
~4:00 am Enrich Receipts Reads each new receipt photo and writes an itemized breakdown into col H, plus the date printed on the receipt (col S) and the merchant (col T).
~5:00 am Assign GL Codes Picks an internal accounting code for each enriched row into col I. Never reaches QuickBooks, never blocks a bill.
every 15 min File-organize retry Files any receipt photo Drive wasn't ready to hand over at submit time.
every 15 min Billing watchdog Notices if a running billing cycle dies partway and emails Matt. Reports only — it never restarts anything.
Why this matters to you A receipt submitted today has no description and no GL code until tomorrow morning. If you run a cycle the same afternoon someone submits, those rows still bill correctly — the invoice just shows the employee's own typed text instead of a tidy itemized breakdown. The amount is never affected.

The two tabs you actually work in

Submissions is the permanent ledger — one row per receipt, forever. Every row carries a Status in col O, and that status is what decides whether it bills.

Reconciliation is a scratch pad, rebuilt from zero every time you parse a statement or re-run matching. One row per charge on the card. This is where you make decisions; nothing you type here is permanent, and that's deliberate.

Non-negotiable

The four standing rules

Everything below follows from these. If something you're about to do would break one, stop and ask Matt instead.

1 · Nothing bills without a matching statement charge

A receipt only becomes billable once the system has found the actual bank charge behind it. This is what stops GPM invoicing an owner for a purchase the card was never charged for. The one deliberate exception is hand-typing Ready yourself — see no charge at all →

2 · The billed amount is always Submissions col K

Amount (Parsed) is a human-entered number. No automatic process ever calculates it, adjusts it, or copies the bank's figure into it. Itemization, approvals and reconciliation change description text and status only. The single exception is Override Amount →, which is itself a figure you type, guarded four ways.

3 · "Col K" means two different things — always say which tab

Naming hazard On Submissions, col K is the dollar amount that gets billed. On Reconciliation, col K is the link that opens the receipt photo. They are unrelated. Never say "col K" without naming the tab.

4 · There are two Lauras

Laura (president) is the one on approvals, summary emails and the CC Laura checkbox. Laura C is a maintenance tech and an ordinary cardholder like anyone else. On the statement she prints differently. Don't merge them on the Cardholders tab.

One time only

Before the very first run

Read this if a cycle has never completed on this sheet Every phase of this system was built and pushed without a full live run, on purpose — one testing layer built once at the end rather than validating each phase as it shipped. The seven items below are the gap between "the code is deployed" and "the first cycle will go cleanly." Skip them and the first run will look broken when it isn't. Once these are done, this section never applies again.

1 · Run Repair GL Chart Numbers once

Maintenance → Repair GL Chart Numbers. Thirty-five account numbers on the GL charts are hyphenated (6100-1), and Google Sheets silently stores some of those as dates — the cell still displays 6100-1 but the code reads "January year 6100." This forces the whole column back to plain text. Only needed after chart data is pasted in, which has already happened.

2 · Fill in the Config tab

These must exist as rows on the Config tab before anything works properly:

  • QB_REIMBURSEMENT_ITEM_ID — the QuickBooks line item every invoice uses
  • STATEMENT_FOLDER_ID — the Drive folder you drop the statement PDF into (the bare ID, not the full URL)
  • STATEMENT_END_DATE — set it to the end date of the newest statement that has already been billed. See Prior Period →
  • ALAINA_EMAIL, LAURA_EMAIL, JASON_EMAIL, MATT_EMAIL

3 · Clear the test keys

The single most dangerous configuration in this system

TEST_EMAIL_OVERRIDE reroutes every email — owner invoices, chase emails, the receipt packet — to one address. If it is set while TEST_MODE is FALSE, a real 200-receipt cycle will send every owner's invoice to that one inbox and report complete success. Nothing errors. You find out when an owner asks where their bill is.

Before the first run: set TEST_MODE to FALSE, and make TEST_EMAIL_OVERRIDE and TEST_ROWS blank. Health Check refuses to pass while that combination exists — believe it.

4 · Seed the noReceipt tab

Most of what's on the company card is not billable to any owner — fuel, car washes, Comcast, Zoom, Intuit, restaurants, parking. On a typical statement that's roughly 226 of 246 charges with no receipt behind them, and every one reads Missing receipt.

The noReceipt tab is the designed suppressor, and it starts empty. A prepared 81-row seed sits at P12_CC_Billing/seed/noreceipt_seed.tsv; pasting it cuts 226 unmatched charges down to 99 and has been checked not to suppress a single charge a real receipt actually matched.

If you skip this Step 6 will email all sixteen cardholders demanding receipts for their lunches and their gas. There is no undo on a sent email.
These are permanent — you never clear them out after a statement Every row in the seed has a blank Amount, which means "this person, this vendor, any amount, forever." The tab is re-read fresh on every match run, so the same rules apply to every future statement. The list is meant to grow slightly each month, never to be reset. See maintaining it over time →

5 · Seed the Merchant Map

Twelve pairings genuinely fail automatic matching — the statement prints RYLEE'S ACE HARDWARE where the receipt says Great Lakes Ace Hardware. Seed from seed/merchant_map_seed.tsv. After the first cycle the system learns new pairings on its own; you never hand-maintain this again.

6 · Deal with receipts older than the statement you're about to run

Some rows on the sheet are dated before the first transaction on the statement you're parsing. They can never match a charge on it. Health Check lists them by row number with a dollar total. Bill them by hand outside the system, then set them to Prior Period — full instructions at stragglers →

Run statements oldest first — skipping one is what creates the mess

It is tempting to skip an older statement to avoid the clutter of a backfill run. It costs far more than it saves. A receipt can only ever match a charge on the statement that charge appears on — so skipping a statement permanently strands every receipt belonging to it, and each one then has to be billed by hand and set to Prior Period individually.

On the current backlog that's the difference between 1 stranded row and 29 ($1,178.38). The 29-row figure is the cost of skipping, not the cost of running.

Running the older statement is also safe for the newer one: receipts dated past a statement's transaction window are excluded from its pool outright — not matched, not listed, status never touched. They wait, untouched, for the statement they belong to.

A backfill run has less work in it than it looks

A catch-up statement shows a lot of Missing receipt rows, because most of the card is spend nobody submits a receipt for. Those are not work. You never act on them row by row — the only thing they feed is whether you click Send Chase Emails.

For a backfill of a period that closed weeks ago, skip Step 6 entirely. Chasing people for months-old purchases is low-yield, and the noise trains everyone to filter the sender before the chase matters. Start chasing on the current statement.

One cosmetic side effect of a backfill run Kickoff renames the Current Statement Drive folder to the period being billed, which sweeps every waiting receipt photo into it — including ones belonging to the next statement. Billing is unaffected (attachments are fetched by Drive file ID, not by folder), and the post-cycle sweep re-files each receipt by its own purchase date once it settles. It corrects itself; nothing to do.

7 · Install the billing watchdog

This one is Matt's — it runs from the Apps Script editor, not the menu (installBillingWatchdogTrigger). Without it, a cycle that dies halfway stops silently: no error, no email, no red row. Health Check reports whether it's installed.

The monthly cycle · Steps 1–8

Start to finish

Do these in order. Steps 4 and 5 loop — you'll review, re-run, review again — and that loop is free. Everything before Step 7 can be undone or repeated. Step 7 cannot.

STEP 1

  • === ACTION REQUIRED === — something blocking is wrong. Do not proceed.

STEP 2

Put the statement PDF in the Drive folder

Drive · nothing to click in the sheet

Download the month's statement from the bank and drop it into the statement folder — the one whose ID is in Config under STATEMENT_FOLDER_ID. Drop it in the folder itself, not into the Processed subfolder.

Exactly one PDF If there is more than one unprocessed PDF sitting there, Step 3 refuses to run rather than guess which one you meant — and it tells you so before spending anything. Move the others out first. Files already in Processed are ignored and can stay.

The statement is from First National Bank of Michigan, processed by Elan Financial. It lists each charge under a cardholder heading printed as LAST,FIRST — for example GREEN,MARTIN W. That heading detail matters in the next step.

STEP 3

Part 1 — Parse Statement

GPM Billing → Part 1 — Parse Statement · free on the normal path

This changed 2026-08-17 — it used to always cost an API call

Parse Statement now tries a deterministic parser first — a Cloud Run service that extracts the PDF with poppler's pdftotext -layout and reads the fixed-width columns with regex. No model, no cost, about 0.2 seconds. It then checks its own answer against the statement's own printed numbers: the purchases total, the credits total, and a subtotal for every individual card — 28 checks on a typical statement, all of which must pass before its answer is trusted.

Claude only runs as the failsafe — when the service is unreachable, not configured, or one of those checks fails (almost always because the bank changed the statement's layout). That's the one case this still costs an API call and takes a minute or two. Either way the report you get and everything downstream — the refusals, the writes, this dialog, reconciliation — is identical.

Then a report appears. Read it — don't just click OK.

Five things in it are worth your attention, in this order:

In the reportWhat you're checking
0. Parser The very first line, and impossible to misread. PARSED BY: the deterministic parser (Cloud Run). No model was used. is the normal case — it also shows the checks-passed count and the poppler build. *** PARSED BY: CLAUDE (FALLBACK) *** means the service couldn't vouch for itself this month; the reason is printed right there, and an error report is filed automatically so the failed layout pattern gets fixed at the source. See the note above for the full two-parser design.
2. Charge total check DELTA: $0.00 ✓ exact means every charge on the statement was read and they sum to the printed purchases total. Anything else and the parse already refused itself — see here →
3. Cardholders found The most likely thing to be quietly wrong on a Claude-fallback parse — the cardholder is a heading, not a column on each line, so it has to be carried down across page breaks. A mistake here doesn't error — it attributes charges to the wrong person, and Step 6 then emails them about it. Check the diff lines: ✓ every statement name matches a cardholder is what you want. On the deterministic path this is one of the 28 self-checks already, so it's confirmed before you even see the report.
4. First 10 charges Spot-check these against the paper statement, line by line. Dates, amounts, vendor text.
5. Credits / refunds Refunds are extracted separately from purchases. If the count looks wrong, or the self-consistency warning appears, don't keep the parse.

Click it once per statement either way. If you just want to re-match after making decisions on the Reconciliation tab, that's Step 5, and it never re-reads the PDF or calls either parser again.

The OK / Cancel decision

OK keeps the parse and immediately runs the first match. The Statements row stays, the Reconciliation tab is filled, and the PDF moves to Processed.

Cancel undoes all of it — the Statements row is deleted, Reconciliation is cleared, and the PDF is moved back to where you found it. Nothing is kept. On the normal (deterministic) path a re-parse costs nothing to redo; on a Claude-fallback parse that API call is spent either way, so Cancel there costs you a re-parse, not a mistake.

Why the dialog can feel slow to appear Everything is written to the sheet before you're asked. That's intentional: the script has a hard six-minute limit and a dialog waiting on a human burns that clock. Doing the writes first means a slow coffee break costs a re-click, not a paid-for parse.

When you click OK, the matching runs immediately and you get a second report — the same one Step 5 produces. That's your starting point for Step 4.

STEP 4

Review the Reconciliation tab

Reading and ticking · nothing here bills anything

This is the human judgement step, and where most of your time goes. Open the Reconciliation tab. One row per charge on the card, in statement order.

The columns you use

col G Status — the system's verdict on this charge. Written by code; don't type here.
col H Receipt Row — which Submissions row it paired with. Yours to edit when you need to narrow a list down to one row.
col K Receipt — a link that opens the photo. Click it before approving anything.
col L Approve — the checkbox. Only appears on rows that can be approved.
col M Notes — why the system decided what it did. Read this first.
col N Override Amount — yours to type, and the only place a dollar figure can be corrected from here.
Anything you type gets wiped on the next re-run — except three things The tab is rebuilt from scratch every time you re-run matching. Only Receipt Row, Approve and Override Amount are carried forward. Don't keep notes anywhere else on this tab; they won't survive.

What each status means and what you do about it

StatusMeaningYour move
Matched Exact cent, right cardholder, dates agree. Decided by code. Nothing. No checkbox appears. It will bill.
Near miss Merchant agrees but the charge is more than the receipt — often an unprinted tip. Open the photo. Then either tick Approve, or type the true figure into Override Amount. Detail →
Over charge The receipt is more than the charge — almost always a decimal typo. Cannot be approved, by design. Fix the amount. Detail →
Double Matched Two or more receipts fit this one charge equally well. The system refuses to guess. Narrow col H to a single row, then tick. Detail →
Merchant Mismatch Amount, cardholder and date all line up, but the vendor names disagree. Open the photo and judge. Tick if it's genuinely the same purchase. Detail →
Date Mismatch Amount and cardholder agree, but the dates are more than 4 days apart. Read the note — it says how far apart. Tick if it's right.
Missing receipt Nothing on the sheet accounts for this charge. Usually nothing — Step 6 chases it. If it's a charge no one should ever be chased for, add a noReceipt rule. Detail →
Skipped (noReceipt) A standing exemption matched — this vendor never has a receipt. Nothing. This is the system working.
Matched (GPM pays) A receipt accounts for it, but GPM eats the cost. Nothing. Never bills, never chased.
Already billed Accounted for by a receipt that went out on an earlier invoice. Nothing.
Matched (row in Error) A receipt matches, but that Submissions row is broken and will never bill as-is. Fix the row, then Fix / Retry Error Rows →
Matched (approved) You ticked it on an earlier pass. The tick stays visible and is revocable. Nothing — unless you've changed your mind, in which case untick.

What ticking Approve actually means

Precise meaning "This charge is accounted for by this receipt — bill Submissions col K as it stands." It approves the pairing, never the amount. Ticking never changes a dollar figure. If the charge and the receipt differ, GPM absorbs the difference, and the note on the row says so explicitly.

Whenever the box is ticked, col H is authoritative. That's what lets you override the system's pick: change the row number, tick, and the pairing follows what you typed. A tick with two or more rows still listed in col H is rejected outright and tells you why — never guessed at.

Below the charges: unmatched receipts

Scroll past the last charge and you'll find a grey separator reading --- UNMATCHED RECEIPTS (no statement charge) ---. These are receipts on the sheet that nothing on this statement pairs with. Each carries a reason. The two you'll see most:

  • "…before this statement's first transaction" — its charge is on the previous statement. Handle →
  • "…after this statement's last transaction" — its charge will land on the next statement. Leave it alone. It stays Pending and matches next month.

Credits and refunds live on their own tab

If the statement had any refunds, a Reconciliation Credits tab is populated too. Every credit needs a tick — even a clean one — because a refund has no receipt total to verify itself against. Full detail →

STEP 5

Part 1 — Re-run Matching

GPM Billing → Part 1 — Re-run Matching (free) · free · repeat freely

Click this after every round of decisions. It costs nothing, calls nothing external, and you can run it twenty times in an afternoon. It reads the charges already on the Reconciliation tab — it does not re-read the PDF.

What one run does, in order:

  1. Applies any Override Amount you typed, writing it into Submissions col K — before matching, so a corrected figure produces an ordinary exact match on this very run.
  2. Re-matches everything from scratch.
  3. Applies your Approve ticks on top of the finished match.
  4. Promotes every cleanly matched receipt from Pending to Ready.
  5. Rewrites the Reconciliation tab and shows you a report.

Read the report's top section first

Under --- Your decisions --- the report lists every override and approval as APPLIED, ACCEPTED or REJECTED. A rejected decision is one you believe you already made — it's listed first precisely so you don't have to go hunting. The reason is also written onto the row itself.

An override is spent whether or not it worked Once a run reads Override Amount, that cell is cleared — accepted or rejected. This is deliberate: it can never be silently applied twice. If yours was rejected, read the reason, fix the cause, and type it again.

Loop between Steps 4 and 5 until the flagged rows are down to ones you've deliberately left alone.

You're ready for Step 6 when Every charge is either Matched, Matched (approved), an accounted-for status, or a Missing receipt you actually want someone chased about.
STEP 6

Send Chase Emails

GPM Billing → Send Chase Emails · emails real people · no undo

Highest blast radius in the project One click emails every cardholder who has a charge with no receipt. It rests entirely on the cardholder headings having been read correctly back in Step 3 — and if one was carried wrong, this emails Riley about John's charges, to their real inbox, with no undo. Do Step 4 and Step 5 fully before you touch this.

It's a separate button on purpose. The review loop guarantees you'll re-run matching several times in one sitting, and bundling the emails in would nag everyone three times an afternoon until they filtered the sender.

A confirmation dialog appears first

It shows you, before anything sends:

  • Every recipient name and the exact address it's going to
  • How many charges and what dollar total each person is being chased for
  • Anyone marked (NO EMAIL — will be skipped)
  • Whether TEST_EMAIL_OVERRIDE is diverting everything

Read the names against the statement before clicking OK. That is the entire purpose of this dialog. Cancel sends nothing.

What actually goes out Each cardholder gets their own email, Receipt needed — <period>, listing only their own charges. Separately, Laura and Jason get one combined digest, Missing receipts — <period>, grouped by person. A cardholder with no email on the Cardholders tab is skipped entirely and appears only in that digest — never defaulted to Laura.

You don't wait for replies. Receipts that come in later ride the ordinary flow: if they're dated inside this statement's window they'll match on the next Re-run Matching; if the statement has closed by then they land as Prior Period.

STEP 7

Part 2 — Invoice & Send

GPM Billing → Part 2 — Invoice & Send · creates real invoices · no undo

This is the irreversible one It creates real QuickBooks invoices and emails them to real property owners. There is no undo, no draft state, and no preview. Everything before this point was reversible; nothing after it is.

What it will bill

Every Submissions row that is Ready at the exact moment you click — nothing else. Not Pending, not Error. That set is frozen the instant the cycle starts, so a receipt submitted while it's running is safely excluded and waits for next month.

Four things can refuse before anything happens

  1. QuickBooks isn't configured — a missing credential. Matt's job.
  2. The test-mode guard — see first-run step 3.
  3. No reconciled statement — the Reconciliation tab must hold charges tagged to the newest Statements row. This is what stops this month's receipts being billed against last month's numbers.
  4. Nothing is Ready — go back to Steps 4 and 5.

Then it runs for 20–30 minutes, mostly without you

Google caps any single script run at six minutes, and a full cycle is far longer than that. So it processes one owner per run and re-schedules itself about sixty seconds later, over and over, until it's done.

Do not click it again while it's running

You'll see a toast reading "Billing started — N owners…", then progress toasts as it works. The menu item itself returns silently — that is normal and is not a failure.

You can close the sheet. It keeps running on Google's servers and emails you when it finishes. Clicking again mid-cycle is caught by a lock and does nothing, but don't rely on that — just leave it alone.

What each owner gets

  • One invoice per owner, not per property. Every property that owner has receipts for appears as its own group of lines on that one invoice.
  • Each line shows the property address (and unit), then the itemized description.
  • Every receipt photo is attached — all pages, for multi-photo receipts.
  • It's addressed to that owner's AppFolio email from PropertyMap col D, copying Alaina, and copying Laura when CC Laura is checked on any of their properties.

Refunds are handled separately: a negative-amount row becomes a Credit Memo rather than an invoice line. Detail →

As each row finishes

It goes Sent with the invoice number in col P — or Error, red, with the reason in col R. An Error row here is a dollar that's stuck, not a dollar that's lost. Recovering it →

  • Run Health Check again. Error count should be zero. If not → Fix / Retry →
  • No rows should still be Ready. Any that are didn't bill — Health Check names them.

Archiving happens by itself

Receipt photos are filed into a folder for the statement period their purchase date falls in. This starts automatically at the end of Step 7 and keeps re-scheduling itself until it's finished — you don't have to notice anything or click anything.

Archive Settled Receipts exists in the menu for the rare case where you want to force it (usually after adding a missing row to the Statements tab). It's safe to run any time and moves nothing that's already filed.

One thing that quietly advances When the cycle completes, Config STATEMENT_END_DATE moves forward to the period you just billed. From then on, a newly submitted receipt dated on or before that date is automatically flagged Prior Period instead of sitting Pending forever with nobody aware. It only ever moves forward, and it is never blanked.

Situations & exceptions

When it isn't the ordinary case

Each of these is linked from the step where you'd hit it. They're written to be read on their own, in whatever order you land in them.

Parse Statement refused

"Parse Statement REFUSED — …"

Five refusals, all checked before any money is spent:

  • More than one PDF in the folder — move all but the current statement out.
  • This exact PDF is already recorded — you've already parsed it. Use Re-run Matching instead; it's free.
  • The newest Statements row already covers this period — a re-download of the same statement is a different Drive file, so this catches what the check above can't. If it genuinely is a new statement, correct or delete the offending Statements row.
  • Open/close dates didn't read as a valid period — nothing was written, the PDF stayed put. Re-run; if it repeats, tell Matt.
  • Charges don't add up to the printed total — see below.

The delta isn't $0.00

"✗ HARD FAIL — charges were dropped or misread"

The parsed charges don't sum to the purchases total printed on the statement. This is a hard refusal, not a judgement call — it means lines were dropped or misread, and every decision downstream is built on that list being complete.

Nothing was written and the PDF was left where it is. Simply run Parse Statement again — it's a fresh read and usually lands. If it fails twice, send Matt the report text; don't try to correct the tab by hand.

Worth knowing The purchases total is a genuinely reliable check. For the July 2026 statement it is $18,590.47 across 249 lines — if you ever re-parse that one, it should tie out to the cent.

Near miss — and how Override Amount works

"charge is $X over the receipt — an unprinted tip? Open the receipt before approving"

The merchant agrees and the cardholder is right, but the bank charged more than the receipt shows. Nearly always a tip added after the receipt printed. Open the photo first — the link is in col K.

Two valid responses:

  • Tick Approve — bills the receipt amount as it stands, and GPM absorbs the difference. The row's note says so explicitly.
  • Type the true figure into Override Amount (col N) — this writes it into Submissions col K so the owner is billed the real total.

The four guards on an override

It is rejected, with the reason written onto the row, unless all four hold:

  1. It's a positive number.
  2. col H names exactly one Submissions row.
  3. That row is currently Pending.
  4. That row is dated on or before this statement's last transaction.

Accepted or rejected, the cell is then cleared — an override can never be spent twice. If yours was rejected, fix the cause and type it again.

Over charge — the one you can't approve

"receipt is $X OVER the charge — likely a decimal typo… this cannot be approved"

The receipt is worth more than what the card was charged. In practice this is almost always a decimal error when the amount was typed — $91.05 entered as $910.50.

No checkbox appears on this status, deliberately. A friendly "approve?" on a row where the receipt is ten times its charge would bill the owner ten times over on one tick.

The fix: correct Submissions col K directly — it's a human-entered figure and you're a human. Then Re-run Matching, and it becomes an ordinary Matched.

Double Matched — two receipts, one charge

"equally good: rows 12, 15 — tick the one you mean"

Two receipts fit this charge equally well on amount, cardholder and date. The system refuses to pick, because picking the first of several equally good candidates is the one thing a matcher gets confidently wrong.

Two common causes, with different fixes:

  • The same receipt was submitted twice. Pick one row to bill; set the duplicate to Non-Billable or leave it Pending to catch a later charge.
  • Two genuinely identical purchases. Membership charges bill as several identical amounts on one day. If there are two charges and two receipts, they both match cleanly on their own and you'll never see this status. You only see it when one receipt is left over.

How to resolve it

  1. Open both photos from the unmatched block lower down the tab.
  2. Edit col H on the charge row so it reads one row number only — delete the rest.
  3. Tick Approve.
  4. Re-run Matching.
A tick alone won't do it Ticking while col H still lists two rows is rejected, with the reason written onto the row. Narrow first, then tick.

The receipts it couldn't choose between also appear in the unmatched block below, each noting which charge is waiting on you — so they don't read as ignored.

Merchant Mismatch

"statement says X, receipt says Y"

Amount, cardholder and date all agree, but the vendor names don't. Normalisation already handles store numbers, city/state suffixes, LLC/INC, payment-gateway prefixes like SQ *, and close spellings — so a mismatch that survives all that is worth a look.

Open the photo. If it's genuinely the same purchase, tick Approve. Once the invoice goes out, the system permanently learns that pairing and never asks you again. Billing is the confirmation event — that's why it learns at Step 7 and not when you tick.

Real examples RYLEE'S ACE HARDWARE ↔ Great Lakes Ace Hardware and SQ *AIR PARK ↔ Grand Rapids Parking are both confirmed genuine. DOLLAR-GENERAL and Family Dollar are different stores and should stay flagged.

Missing receipt — and suppressing the ones that don't need chasing

Dozens or hundreds of charges reading "Missing receipt"

Most of what's on the card is not billable to any owner: fuel, car washes, Comcast, Zoom, Intuit, subscriptions, restaurants, parking. Left alone, every one reads Missing receipt and Step 6 chases someone for it.

The fix: a noReceipt rule

Add a row to the noReceipt tab:

col A Cardholder — either the employee name or the printed statement name; both work.
col B Vendor — matched by containment against the statement's vendor text.
col C Amount — optional. Blank suppresses any amount; a figure suppresses only that exact one.
Keep vendor strings specific Because it matches by containment, a vague string covers far more than you intend. Prefer MISTER CAR WASH over WASH. Anything under three characters is rejected outright; everything else is judged by what it actually suppressed, so a short but specific name like VIOC is fine.

These rules are permanent — and there is no monthly cleanup

A rule with a blank Amount means "this person, this vendor, any amount, forever," and the tab is re-read on every match run. You never clear the list out after a statement. The spend it describes — fuel, subscriptions, vehicle servicing, lunches — recurs every single month, so clearing it would simply regenerate the same noise next cycle.

ADD When a new recurring vendor shows up as Missing receipt noise that nobody should ever be chased for. A handful of rows a year, at most.
REMOVE Only when an exemption has become wrong — that person has started submitting genuinely billable receipts for that vendor. Rare. Never as routine maintenance.

The rows worth an occasional second look are dual-use stores that sell both groceries and property supplies: MEIJER, AMAZON, AUTOZONE, DOLLAR-GENERAL. The vehicle-service rows (VIOC, MUFFLER MAN, KOOL CHEVROLET) are safely permanent — GPM pays those regardless of property.

How the report tells you a rule got too broad You'll see a noReceipt warning when a single rule turns out to have covered two or more different merchants on one statement — it names them so you can confirm none should have been chased. That's the signal worth reading. A rule covering one merchant, however short its name, never warns.

Exemptions are applied only to charges nothing matched, so a rule can never suppress a charge a receipt actually paired with.

The one narrow risk of an exemption If a receipt exists but fails to match — wrong amount typed, date outside the gate — then its charge is unmatched, and an exemption will make it read Skipped (noReceipt) rather than Missing receipt. The receipt is not lost: it still appears in the unmatched-receipts block lower on the tab. But you lose one of the two signals pointing at it, so scan that block even on a statement with few missing receipts.

Also check: a cardholder whose Statement Name is blank on the Cardholders tab has every charge read as Missing receipt. The reconcile report names them under "Cardholders with no Statement Name."

A receipt with no charge on this statement

A row in the unmatched block below the separator

Read its note — it always gives a reason now. The three cases:

  • Dated after this statement's last transaction. Its charge posts on the next statement. Do nothing. It stays Pending and matches next month.
  • Dated before this statement's first transaction. Its charge was on the previous statement. If that one is already billed, treat it as a straggler — here →
  • "no charge on this statement matches this amount." Either the amount typed is wrong, or the purchase genuinely hasn't hit the card yet. Check the photo against col K.

A receipt you must bill with no statement charge at all

Rare, and always a deliberate decision

Rule 1 says nothing bills without a matching charge. The escape hatch is to type Ready into Submissions col O yourself — either directly or via Set Status for Row(s)…, which is safer because it checks and colours the row.

A hand-typed Ready is never downgraded by a later re-match; status writes from reconciliation only ever upgrade. So it will survive until it bills.

You are taking the rule off You're asserting the charge exists without evidence on the statement. Be sure, and be able to say why later.

Prior Period and stragglers

Health Check: "N Pending/Ready row(s) dated before …"

A receipt whose purchase date falls inside a statement that has already closed and billed can never match automatically — that statement's Reconciliation tab was overwritten long ago. Left alone it sits Pending forever with nobody aware.

Going forward, this is automatic

A newly submitted receipt dated on or before Config STATEMENT_END_DATE lands as Prior Period at submission, and Laura gets a batched digest about it roughly ten minutes later (one email for ten late receipts, not ten emails).

For rows already on the sheet

  1. Bill them by hand outside the system.
  2. Set Status for Row(s)… → enter the rows (accepts 14, 14-19, or 14,15,20-25) → type Prior Period.
  3. Confirm the preview. Each row records the transition in col R.
Prior Period, not Non-Billable Non-Billable means "GPM pays this" and keeps the row in the matching pool, where a same-amount charge from a later month can be proposed against it. Prior Period removes it from the pool entirely and lets it archive. They are not interchangeable.

Prior Period is a status nothing else recognises — that is the whole mechanism. Enrichment skips it, GL skips it, billing never picks it up, reconciliation excludes it. Archiving does file it, correctly, by purchase date.

Refunds and credits

A Reconciliation Credits tab appears

A refund is submitted through the same form with a negative amount. It rides the same Pending → Ready pipeline, distinguished only by sign. Statement credits are extracted separately from purchases and matched on their own tab.

Every credit needs a tick — even a clean one A purchase verifies itself: the itemized receipt has to sum to the billed amount. A credit has no such check, so your approval is the safety rail. Nothing on this tab is ever processed automatically, however good the match.

The two proposals

  • "Refund — would net, no bill" — exactly one unbilled purchase for that same owner matches the credit to the cent. Approving marks both rows Netted — No Bill. Neither bills; no QuickBooks document is created at all.
  • "Refund — would credit" — no single clean offset (or several equally good ones, which is too ambiguous to net). Approving promotes the row to Ready, and Step 7 creates a Credit Memo in QuickBooks.
Credit Memos show as "unsent" in QuickBooks — that's correct A Credit Memo is deliberately never emailed to the owner. It sits open and nets against that owner's next invoice automatically, provided Automatically apply credits is on in QuickBooks Advanced settings. It is not a bug and needs no action.

Credits have no earliest-date limit, on purpose: a refund routinely posts a statement or two after the purchase it reverses, and the row is often dated against that original purchase.

Refund receipts are itemized too (fixed 2026-08-13) A refund's negative col K used to be skipped by both the nightly enrichment sweep and GL coding, so it billed off the employee's raw typed text with no GL code and no merchant for this matcher to read. Refunds now enrich like any other receipt — the vision pass reconciles against the magnitude; only the Submissions cell itself carries the minus sign.

Error rows — recovering a stuck dollar

Red rows; Health Check warns with a count and the oldest date

Nothing retries on its own. Read col R, fix whatever was actually wrong — a PropertyMap gap, a bad amount, a QuickBooks issue — and then run Fix / Retry Error Rows.

It sorts every Error row into one of three repairs based on what's on the row, never by reading the note text:

Row looks likeWhat it does
No owner, no QB ID, no invoice # Never made it through intake. Re-runs the full classification a fresh submission would get, and lands on whatever the current data resolves to.
Owner and QB ID filled, no invoice # Already reconciled, then failed later. Re-checks PropertyMap and validity and restores straight to Ready — never back through reconciliation, which would risk matching against a different statement.
Invoice # is filled The QuickBooks document already exists; only attaching or sending failed. Retries only those, against the existing document.
Never hand-flip a row that has an invoice number back to Pending A fresh cycle has no memory of the earlier document. It would create a second invoice and bill the owner twice for the same receipt — the original invoice's lines are still there and already marked Sent. This is why Set Status for Row(s)… refuses any row with an invoice number outright. Use Fix / Retry, which repairs the existing document.

Rows sharing an invoice number are repaired together, and every file on the group is re-attempted. Worst case is a duplicate photo attachment or a duplicate send email — never a duplicate charge.

The cycle stopped and never emailed you

Alert to Matt: "cycle STALLED", or simply no completion email

The cycle advances by scheduling its own next run, so an execution that dies outright leaves it stopped with saved state and nothing scheduled to continue. The watchdog notices within about fifteen minutes and emails Matt. It reports only — it never restarts anything, because restarting a cycle it doesn't understand is how a stuck run becomes a double bill.

To resume

Click Part 2 — Invoice & Send again. It picks up from the saved state: owners already done are skipped, and an owner whose invoice already exists is resumed, never recreated. The invoice's ID is saved before the first attachment is even attempted, precisely so a second one is impossible.

Health Check also reports an in-flight cycle, naming the period, how many owners remain and how long since it last advanced.

GPM Contracted Work — assigning an owner by hand

Health Check: "N Ready row(s) still need Owner Name + QB Customer ID"

GPM Contracted Work behaves like any property except that the owner changes with every receipt, so it can't be looked up. Intake leaves the owner blank and the row goes Pending normally; reconciliation matches and promotes it to Ready without caring who eventually pays.

You type the owner directly onto the Submissions row — Owner Name in col L and QB Customer ID in col M — any time before Step 7. There's no special tool and no special status.

Do it before you run Part 2 A row still missing a QB Customer ID at Step 7 is flagged Error and doesn't bill that cycle. It's recoverable with Fix / Retry, but Health Check lists these before a cycle runs for exactly this reason — deal with them then.

If the owner is a brand-new QuickBooks customer, create them in QuickBooks first, then paste their ID in. Nothing here creates customers.

A description or GL code is wrong

col H reads oddly, or col I is blank or clearly miscoded

Use Fill GL Code / Description for Row(s)…. Give it a row or a range, choose description, gl, or both, and confirm.

It always overwrites, unlike the nightly sweeps which never touch a filled cell. That's the point: the sweeps' caution exists to make unattended runs safe, and this is neither unattended nor blind. It works on any row regardless of status — both fields are internal-only and never reach an invoice that's already been created.

Why a description might have fallen back to one line If the receipt's own numbers don't reconcile to col K within ten cents, the row deliberately falls back to a single line and gets a note in col R. A breakdown scaled onto a total it doesn't actually match would read as verified when nothing was verified. Fix the amount, then re-fill.

A receipt that needs more than one photo

The form accepts up to five files per submission, and every stage treats a row's receipt as the whole set: all pages are filed together, read as one document, attached to the invoice, and included in Alaina's packet. col N holds one link per line.

If someone forgot a page after submitting, they resubmit the whole receipt fresh with all photos attached. There's no way to append to an existing row. Then set the incomplete row to Non-Billable so it doesn't double-match.

GPM Pays (Non-Billable)

Receipts submitted against the GPM Pays property choice never bill an owner. They land Non-Billable immediately, skip enrichment and GL coding, and are never chased. They still account for their statement charge — showing as Matched (GPM pays) — which is what keeps them out of the Missing receipt noise.

"Possible duplicate — verify"

A note, never a rejection. Same employee, same amount, same day. It's a warning because legitimate duplicates are common — memberships bill as several identical charges on one card on one day.

Real double-submissions surface later as Double Matched →, judged against what the bank actually charged rather than guessed at before the statement exists.

How the Reconciliation tab actually decides

Step 4 tells you what each status means and what to do about it. This is the mechanics underneath — every column on both tabs, and the exact order the matcher works in. You don't need any of this to run a cycle; it's here for when a status surprises you and you want to know why, or when you're deciding whether a noReceipt rule or a Merchant Map entry will actually catch what you think it will.

Every column on the Reconciliation tab

A–O, rebuilt from nothing on every parse or re-match. Three columns are yours; the rest are written by code and overwritten on the next run.

A–C Post Date, Trans Date, Ref # — copied straight off the statement line. Trans Date is what matching actually gates on; Post Date is display only.
D · E Cardholder, Vendor — the statement's own text, unmodified. Cardholder is looked up against Cardholders col C to find the employee; Vendor is what the merchant-agreement scoring compares against Submissions col T.
F Amount (charge) — what the bank actually charged. Never written to; this is the number everything else is judged against.
G Status — the verdict. Code-written; see the matching order below for exactly how it's chosen.
H Receipt Row — the Submissions row it's paired with. Yours to narrow when several rows tie; whenever Approve is ticked, this cell is authoritative over whatever the matcher picked.
I · J Receipt Amount, Difference — read-only, shown only when they differ from the charge or the status needs a checkbox. Receipt Amount is never editable; correcting a figure always goes through Override Amount (col N) instead, so no single cell is ever both an input and an output.
K Receipt — a link to the first photo page. Naming hazard: this is a different col K than Submissions' — see the standing rules at the top of this runbook.
L Approve — checkbox, only inserted on rows a decision actually applies to (never on Matched — nothing to decide — and never on Over charge, where a tick would bill the owner for a typo).
M Notes — the system's reasoning for this row, rebuilt fresh every run. Nothing you type here survives a re-run; there's no other place on this tab that does either.
N Override Amount — yours to type. The only place a dollar figure gets corrected from this tab; see the four guards under Near miss →.
O Statement Period — the label from Statements, stamped on every row so a stray filter or sort never mixes two statements' charges together.

The matching order, exactly

One pass decides most of a statement outright, a narrow post-pass catches the one thing a greedy pass would get confidently wrong, and a second pass mops up everything left on both sides. Every charge lands in exactly one of these, in this order:

  1. Pass 1 — exact cent, right cardholder, inside the date gate. For each charge, every not-yet-consumed receipt from the same employee, matching to the exact cent, dated within RECON_DATE_GATE_DAYS (4 days) of the charge's transaction date, is scored. Merchant is not a filter here — a blank Cleaned Merchant (col T) must never read as a miss — it only ranks candidates: best merchant agreement first, then the closest date, then the earliest Submissions row, so a re-run is always deterministic. The winner becomes Matched, or Merchant Mismatch if the vendor names actively disagree.
  2. Post-pass — was the winner only the first of several equally good? Computed against the finished pass, not during it, because releasing mid-loop would cascade. If any other receipt tied the winner on both merchant score and day gap and is still unconsumed, the pairing is undone and the charge becomes Double Matched, listing every tied row. Two genuinely identical purchases with two identical receipts never trigger this — both sides consume cleanly. It only fires when one receipt is left over.
  3. Pass 2a — same cent amount, only the date is in question. Everything still unassigned, on both sides, gets one more look: if a same-employee receipt matches the amount exactly but sits outside the date gate (or has no usable date at all), the nearest one by days wins. No merchant requirement — an exact-cent match on the right person is already strong enough that requiring a merchant would strand every receipt with a blank col T. Result: Date Mismatch.
  4. Pass 2b — the amounts genuinely differ. Last resort, and the only pass that requires a confirmed merchant match — it's the only thing that makes proposing a different-amount pairing defensible at all. Among same-employee, merchant-confirmed receipts, the closest amount wins. The charge being more than the receipt (an unprinted tip) is Near miss; the receipt being more than the charge (almost always a decimal typo) is Over charge — which, deliberately, can never be approved.
  5. Nothing matched. A standing noReceipt exemption is checked only now — never earlier, so a real receipt can never be suppressed by a rule that happens to fit. A hit is Skipped (noReceipt); no hit is Missing receipt.
A matched receipt that can never bill still counts as accounted-for A Non-Billable, Sent or Error receipt still enters every pass above like any other — it just can't be promoted to Ready. A successful pairing there reads Matched (GPM pays), Already billed, or Matched (row in Error) instead of Matched. Without this, every GPM-paid or already-invoiced charge would read Missing receipt every single month and bury the real misses in noise.

Every column on Reconciliation Credits

A–L, same rebuild-every-run discipline. A credit is matched by the identical algorithm above, run against a pool of submitted refund rows instead of purchases — what differs is entirely what happens after a pairing is found.

A–F Post Date, Trans Date, Ref #, Cardholder, Vendor, Amount (credit) — same meaning as the purchase tab's A–F.
G Status — one of the two proposals below, or a passed-through Double Matched / Over charge if the underlying match itself was ambiguous, which is left for you to resolve exactly as it would be on the purchase tab.
H · I Credit Row, Offset Row — both code-derived (the matcher and the netting search below). Never yours to type; there's no Receipt Row-style override here.
J Approve — the only human column this tab has. Ticked on both proposal statuses, deliberately, since a refund has no itemized receipt total to verify itself against the way a purchase does.
K · L Notes, Statement Period — same role as the purchase tab's M and O.

The netting search

Once a credit is paired with a submitted refund receipt, one more search decides which of two proposals to make — never processed automatically either way, however clean the match:

  1. Look across every other currently-unbilled row (Pending or Ready) for the same owner — by QB Customer ID, across all of that owner's properties, not just the one the credit posted against — that matches the credit's amount to the cent.
  2. Exactly one candidate → Refund — would net, no bill. Approving marks both rows Netted — No Bill directly on Submissions. Neither bills; no QuickBooks document is created at all.
  3. Zero, or two-or-more, candidates → Refund — would credit. Two-or-more is the same "never guess on a tie" rule Pass-1's post-pass lives by — picking one of several equally good offsets would be a guess, so it falls through to a plain proposal instead. Approving promotes the row to Ready; Step 7 is what actually raises the Credit Memo in QuickBooks.

What's cleared and what survives a re-run is the same rule as the purchase tab — see the warning under Step 4.
